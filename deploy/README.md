# Установка готового релиза

Пользовательский установщик поддерживает Ubuntu/Debian с systemd и публичным
IPv4. Нужен домен с единственной A-записью на IPv4 VPS, без AAAA и CDN-прокси.
Docker Compose должен быть версии 2.24.4 или новее. При отсутствии Docker
мастер предлагает установить его из официального apt-репозитория Docker.
Firewall провайдера установщик не изменяет: разрешите TCP 80, 443, 3478 и
UDP 3478, 55000–55039. При выпуске сертификата Let's Encrypt проверяет доступ
снаружи; локальная проверка свободных портов не гарантирует доступ через firewall.

## Отдельный сервер ключей

Поддерживается начиная с **FamilyChat v2.3.0**. Готовый комплект содержит
`compose.keyserver.yaml` и признак `external_key_service: 1` в `release.json`.
Установщик откажется подключать службу к более старому комплекту.
Клиенты iOS/macOS/Android также должны поддерживать
отдельный сервер ключей: сначала обновите приложения, затем переключайте API.

### 1. Установите службу на другом хостинге

На отдельной Ubuntu/Debian машине подготовьте `curl` и CA-сертификаты.
Домен `keys.example.com` должен указывать на этот хост. Запустите независимый
установщик:

```sh
curl -fsSL https://github.com/balamutik/familychat-keyserver/releases/latest/download/install.sh | sudo bash
```

Либо используйте установщик основного проекта с выбором сервера ключей:

```sh
curl -fsSL https://github.com/balamutik/familychat-server/releases/latest/download/install.sh | sudo bash -s -- --key-server
```

Параметры можно передать сразу, например для Certbot и свободного порта 80:

```sh
curl -fsSL https://github.com/balamutik/familychat-keyserver/releases/latest/download/install.sh | sudo bash -s -- --domain keys.example.com --email owner@example.com --client certbot
```

Для acme.sh используйте `--client acme.sh`; варианты `--challenge webroot` и
`--challenge dns` и установка DNS-плагинов описаны в
[README службы](https://github.com/balamutik/familychat-keyserver#readme). API ключей
слушает **TCP 8443**, номер меняется через `--port`. Порты 443 и 8080 не используются.
**HTTP-01 проверка сертификата требует внешний TCP 80**, независимо от порта API.
Если 80 занят, установщик не останавливает другое приложение: выберите существующий
webroot либо DNS-01. DNS-01 не требует свободных входящих 80/443.

Файл подключения появится в
`/opt/familychat-keyserver/export/main-server.json`. Он содержит публичный ключ,
URL и секрет подписи билетов, **не содержит приватного ключа переписки**. Скопируйте
его на основной хост по SSH, например в `/root/main-server.json`, и оставьте права 0600.
Каталог `state/` и приватные материалы службы на основной хост не копируются.

### 2. Новая установка основного сервера

Передайте путь к конфигурации. При этом локальная приватная пара на основном
сервере не создаётся:

```sh
curl -fsSL https://github.com/balamutik/familychat-server/releases/latest/download/install.sh | sudo bash -s -- --key-service-config /root/main-server.json
```

Установка из исходного кода:

```sh
cd /path/to/FamilyChat/server
mkdir -p secrets
# Подготовьте .env и secrets/admin-password.txt по разделу ручного запуска README.
sudo install -o 10001 -g 10001 -m 0400 /root/main-server.json secrets/key-service.json
printf '\nKEY_SERVICE_CONFIG_FILE=./secrets/key-service.json\n' >> .env
scripts/deploy-https.sh up --host chat.example.com --letsencrypt --email owner@example.com
```

Скрипт автоматически добавляет `compose.keyserver.yaml` и пропускает локальный
`key-setup`. При самостоятельных командах Compose добавляйте этот файл явно:
`docker compose -f compose.yaml -f compose.https.yaml -f compose.keyserver.yaml ...`.
Прямой запуск бинарника использует `CONTENT_KEY_SERVICE_FILE=/путь/main-server.json`;
файл должен иметь права 0400/0600 и быть доступен пользователю API.

### 3. Перенос уже работающего сервера без потери истории

1. Обновите приложения и основной сервер до версии с этой функцией. Сохраните
   согласованную резервную копию БД, файлов и исходных ключей вне обоих серверов.
2. При установке отдельного сервиса **импортируйте существующую пару**, вместо
   генерации новой: добавьте к команде `scripts/install.sh` параметры
   `--import-public /root/content-public-key.txt --import-private /root/content-private-key.txt`.
   Эти два файла берутся из `/opt/familychat/secrets/` старой установки и передаются
   только на хост ключей по SSH. Для прежнего `key.json` используется `--import-json`.
3. Перенесите экспортированный `main-server.json` на основной хост и выполните:

```sh
sudo familychat configure-key-server --key-service-config /root/main-server.json
sudo familychat status
```

Команда сравнивает публичный ключ с исходным и отказывается применять другую пару.
API повторно проверяет отпечаток по БД; существующая история не перешифровывается.
Неподходящая пара не заменяется автоматически. API перезапускается без подключения
приватных secrets, nginx перечитывает адрес API. Вход пользователей остаётся прежним.

**Прежние приватные файлы не удаляются автоматически.** Сначала проверьте чтение
старых сообщений и файлов на обновлённом приложении и наличие проверенной внешней
резервной копии. Затем уберите с основного хоста `secrets/content-private-key.txt`,
старый том `familychat_encryption_keys`, копии `key.json` и прежние резервные копии,
содержащие приватный ключ. Точное имя тома зависит от имени проекта Compose:
проверьте его через `docker volume ls`; не удаляйте тома БД или файлового хранилища.
Отключение secret mount само по себе не стирает ключ с диска и старых снимков VPS.

### 4. Обновление, сертификаты и восстановление

На хосте ключей используйте собственные `scripts/update.sh`, `scripts/renew.sh`
и `scripts/backup.sh`; инструкции и восстановление резервной копии — в его README.
Обновление сохраняет пару и секрет билетов. Продление запускается отдельным
systemd timer; новый сертификат подхватывается без перезапуска основного приложения.
Проверьте доступность `https://keys.example.com:8443/health/ready` с клиентской сети.

Основной сервер обновляется обычной командой `sudo familychat update`. Настройка
отдельной службы сохраняется; откат на комплект без её поддержки блокируется.
При потере устройства пользователь входит на новом устройстве, клиент заново
получает ключ через HTTPS. Пароли и регистрацию второго аккаунта вводить не нужно.
Если служба временно недоступна, устройства с уже сохранённой парой не скачивают
её повторно; новый вход без локальной пары требует доступной службы. Основной API
при запуске не подключается к ней и не скачивает приватный ключ.

## Подготовка зависимостей

Команды выполняйте через SSH в интерактивном терминале, используя пользователя
с правами `sudo` (либо root). Сначала установите базовые зависимости:

```sh
sudo apt-get update
sudo apt-get install -y curl ca-certificates python3 openssl
```

`curl` нужен ещё до запуска установочной команды. Python 3 запускает мастер,
CA-сертификаты нужны для HTTPS-загрузок, OpenSSL — для работы с ключами.
Git, Go, Node.js и локальная сборка образов для установки готового релиза не нужны.

Если Docker не установлен, запускайте установщик ниже: он предложит установить
Docker Engine и Compose из официального репозитория Docker и запустить службу.
Если Docker уже есть, заранее проверьте **обе** команды:

```sh
sudo docker info
sudo docker compose version
```

Наличие команды `docker` не означает наличие Compose. Установщик v2.1.0
не устанавливает недостающий Compose автоматически при уже установленном Docker;
в этом случае он может завершиться сообщением `docker (код 125)`.
Начиная с v2.2.0 это исправлено: новый установщик проверяет базовые зависимости,
предлагает установить недостающие пакеты и повторно проверяет результат.
При отсутствующем или устаревшем Compose он выбирает пакет по установленному
`docker.io` либо `docker-ce-cli`, не заменяя сам Docker Engine. Если источник
Docker неизвестен или доступный пакет слишком старый, выводится понятная ошибка.
Команды ручной подготовки ниже полезны для диагностики и установки v2.1.0. Перед установкой пакетов запрашивается подтверждение.
Старая отдельная команда `docker-compose` не заменяет требуемый плагин
`docker compose` версии 2.24.4 или новее.

### Ubuntu 24.04: Docker из репозитория Ubuntu

Если используется пакет `docker.io`, установите Compose из того же репозитория:

```sh
sudo apt-get update
sudo apt-get install -y docker-compose-v2
sudo systemctl enable --now docker
sudo docker info
sudo docker compose version
```

Для чистой Ubuntu 24.04 вместо автоматической установки Docker мастером можно
заранее установить оба пакета: `sudo apt-get install -y docker.io docker-compose-v2`.
Пакет [docker-compose-v2](https://packages.ubuntu.com/noble/docker-compose-v2)
находится в компоненте `universe`. Если apt не находит его, проверьте, включён ли
`universe` в источниках Ubuntu, и повторите `sudo apt-get update`.

### Docker из официального репозитория Docker

Если Docker установлен как `docker-ce`/`docker-ce-cli` и его apt-репозиторий
уже подключён, пакет плагина называется иначе:

```sh
sudo apt-get update
sudo apt-get install -y docker-compose-plugin
sudo docker compose version
```

Не устанавливайте одновременно оба варианта плагина и не смешивайте пакеты
Docker Engine разных поставщиков. Определить установленные пакеты можно командой:

```sh
dpkg-query -W docker.io docker-ce docker-ce-cli docker-compose-v2 docker-compose-plugin 2>/dev/null
```

Для Debian или другой поддерживаемой Ubuntu следуйте инструкции
[Docker Engine для Ubuntu](https://docs.docker.com/engine/install/ubuntu/)
или [Docker Engine для Debian](https://docs.docker.com/engine/install/debian/),
затем [установке Compose plugin](https://docs.docker.com/compose/install/linux/).
Команды для пакета Ubuntu 24.04 выше не следует переносить на Debian без проверки.

Если `sudo docker info` не выполняется, сначала проверьте службу:

```sh
sudo systemctl status docker --no-pager -l
sudo journalctl -u docker -n 80 --no-pager
```

Продолжайте установку, когда Docker отвечает и версия Compose соответствует
требованию. Добавлять пользователя в группу `docker` для установки через `sudo`
не требуется.

## Запуск установки

Перед установкой проверьте свободное место:

```sh
df -h /
docker system df # если Docker уже установлен
```

Практический ориентир: диск от 25–30 ГБ и не менее 3 ГБ свободного места перед
установкой или обновлением. Это рекомендация, а не гарантированный минимум:
учитывайте размер вложений, журналов и запас для миграций PostgreSQL.
Новый образ скачивается до очистки старого.

Установка последнего стабильного релиза:

```sh
curl -fsSL https://github.com/balamutik/familychat-server/releases/latest/download/install.sh | sudo bash
```

Введите домен и email для сертификата. Авторизация в registry не нужна, если
репозиторий и пакет GHCR публичные. Установка создаёт `/opt/familychat` (0700):
служебный `.env` и состояние (0600), закрытый каталог `secrets`, сертификаты
`.https` и каталоги версий `releases`. API запускается не от root, поэтому
смонтированный файл первого пароля читается контейнером; его каталог на VPS
доступен только root. Пароль не записывается в Git и не входит в релиз.

Команды после установки:

```sh
sudo familychat status                 # версия и состояние контейнеров
sudo familychat logs                   # последние записи и поток журналов
sudo familychat update                 # последний стабильный релиз
sudo familychat update --version v2.2.0 # конкретный опубликованный релиз
sudo familychat renew                  # ручное продление сертификата
sudo familychat configure-push         # шлюз iOS/Android, прямой APNs или отключение
```

`familychat-renew.timer` ежедневно запускает продление HTTPS. Состояние таймера:
`systemctl status familychat-renew.timer`. Первые учётные данные показываются
после создания администратора. Исходный пароль хранится в
`/opt/familychat/secrets/admin-password.txt`; после смены пароля в приложении
этот файл не отражает новый пароль.

Обновление запрашивает подтверждение готовности резервной копии. Сохраняйте
согласованную копию PostgreSQL и файлового хранилища, а также `/opt/familychat`
(секреты и сертификаты). Файлы `secrets/content-public-key.txt` и
`secrets/content-private-key.txt` содержат общую пару шифрования и обязательно
входят в резервную копию. Перед переходом с v2.0.0 сохраните также том
`familychat_encryption_keys`: установщик перенесёт из него ту же пару в Docker
secrets. API получит два секрета только для чтения, worker их не получает.
Томам данных всегда назначаются имена
`familychat_postgres_data` и `familychat_s3_data`, независимо от версии релиза.
Данные не входят в образ. Не удаляйте тома через `docker compose down -v`.
Миграции применяются при запуске: выбор старой версии не откатывает схему БД.
Начиная с v2.2.0 после успешной проверки готовности установка и обновление очищают неиспользуемые
образы с меткой FamilyChat. Образы, используемые любыми контейнерами, сохраняются;
чужие образы, контейнеры и тома данных не удаляются. Ошибка очистки выводит
предупреждение и не отменяет установку.
При ошибке после начала активации установщик сохраняет номер незавершённого
релиза. Повторите ту же установочную команду или `familychat update` без версии,
чтобы продолжить. Автоматического отката миграций нет.

Старые установки из Git не импортируются автоматически: установщик не
перезаписывает найденные настройки, не использует чужие тома и проверяет
занятость портов. Продолжайте обновлять такую установку прежним способом либо
отдельно перенесите данные и настройки. APNs требует вашего ключа Apple
Developer; мастер его не создаёт. Без APNs чаты и звонки работают при открытом
приложении, фоновые push-уведомления iOS требуют отдельной настройки.

## Восстановление после ошибок

Строка `Ready: https://...` подтверждает ответ HTTPS на одном из этапов.
Дождитесь завершения всей команды: падение TURN или другого контейнера после
этой строки означает, что обновление не завершено. Проверяйте:

```sh
sudo familychat status
docker ps -a --filter label=com.docker.compose.project=familychat
```

### Закончилось место: No space left on device / SQLSTATE 53100

Сначала определите, что занимает диск:

```sh
df -h /
docker system df
sudo du -xhd1 /var /opt /root 2>/dev/null
sudo journalctl --disk-usage
```

Для освобождения места можно удалить неиспользуемые образы и кэш сборки.
Эти команды затрагивают неиспользуемые образы и кэш всех проектов на хосте;
образы, связанные даже с остановленными контейнерами, сохраняются.
Проверьте предлагаемые изменения перед подтверждением:

```sh
sudo docker image prune -a
sudo docker builder prune
sudo apt-get clean
```

Если много места занимают журналы systemd и старые записи больше не нужны:

```sh
sudo journalctl --rotate
sudo journalctl --vacuum-size=200M
df -h /
```

Последняя команда очистки удаляет старые журналы, но не данные чатов.
Не используйте `docker volume prune`, `docker compose down -v` и ручное удаление
файлов из `/var/lib/docker` или каталога PostgreSQL: можно потерять данные.
При нехватке места после очистки увеличьте диск VPS.

Миграции выполняются в транзакции. После освобождения места повторите обновление:

```sh
sudo familychat update
sudo familychat status
```

Установщик продолжит сохранённую незавершённую версию. Не меняйте вручную
таблицу миграций и не выбирайте другую версию до завершения восстановления.

### Контейнер TURN завершился с кодом 139

Код 139 обычно означает SIGSEGV. Причину нужно установить по журналам;
сам по себе он не доказывает нехватку памяти или ошибку настроек.
Соберите диагностику перед повторным запуском:

```sh
docker logs --tail 100 familychat-turn-1
docker inspect --format 'status={{.State.Status}} exit={{.State.ExitCode}} oom={{.State.OOMKilled}}' familychat-turn-1
free -h
df -h /
sudo journalctl -k -n 80 --no-pager
```

Для передачи диагностики не публикуйте `.env`, полный `docker inspect`,
содержимое `secrets` или ключи APNs. Просмотрите журналы и скройте секреты,
если они туда попали. После устранения причины продолжите `sudo familychat update`.
Успешный ответ `/health/ready` не подтверждает работу звонков через TURN:
звонок нужно отдельно проверить между устройствами в разных сетях.

## Выпуск версии владельцем проекта

Workflow `.github/workflows/release.yml` запускается при пуше тега `vX.Y.Z`.
Он проверяет установщик, собирает образ для `linux/amd64` и `linux/arm64`,
публикует его в `ghcr.io/balamutik/familychat-server`, затем создаёт GitHub Release
с `install.sh`, `familychat-server.tar.gz` и `SHA256SUMS`. API, worker и подготовительный key-setup в комплекте
используют один digest образа; исходники, `.env` и секреты туда не входят.
Изменение файлов конфигурации доставляется вместе с новой версией образа.

Следующий выпуск после проверки изменений (замените `vX.Y.Z` новым номером):

```sh
git tag vX.Y.Z
git push origin vX.Y.Z
```

Номер версии выбирает владелец. Опубликованные релизы не перезаписываются.
Для доступа других людей владелец отдельно делает публичными репозиторий GitHub
и пакет Container Registry (Package settings → Change visibility → Public).
В приватном репозитории сборка/публикация возможна, но анонимная установка
недоступна. Смена видимости репозитория сама по себе не заменяет проверку
доступности пакета GHCR. Workflow использует встроенный `GITHUB_TOKEN` с правами
`contents: write` и `packages: write`, дополнительных секретов ему не нужно.

Проверки установщика без изменения VPS:

```sh
python3 -m unittest discover -s tests/installer -v
bash -n install.sh scripts/deploy-https.sh
shellcheck install.sh
```

Проверка сгенерированного Compose (не запускает сервисы):

```sh
python3 tests/installer/validate_compose.py /path/to/familychat-server.tar.gz
```
 Полный сценарий
Docker/systemd/Let's Encrypt необходимо проверять на отдельном VPS с DNS;
unit-тесты не подтверждают публичную доступность и работу TURN.

# HTTPS-развёртывание сервера

Команды выполняются из каталога `server`. Сначала заполните `.env` по образцу
`.env.example` и создайте `secrets/admin-password.txt`. Скрипт собирает образы
API и worker, запускает PostgreSQL, хранилище файлов, TURN, API, worker и nginx.
В этом режиме порт API `8080` не публикуется; nginx принимает `80/443` и
проксирует **все HTTP-маршруты**, включая `/admin/`, API, WebSocket и файлы.

Для сертификата и ключа в формате PEM:

```sh
scripts/deploy-https.sh up --host chat.example.com \
  --cert /path/to/fullchain.pem --key /path/to/privkey.pem
```

Сертификат должен содержать выбранный DNS-адрес или IP в Subject Alternative
Name. Файлы копируются в игнорируемый Git каталог `.https/certs`, поэтому
исходные PEM-файлы должны оставаться доступными только администратору.

Для тестирования на собственном IP, например в локальной сети:

```sh
scripts/deploy-https.sh up --host 192.168.1.20 --self-signed
```

Самоподписанный сертификат нужно добавить в доверенные на каждом клиентском
устройстве; иначе приложение не установит HTTPS-соединение. Сертификат
сохраняется в `.https/certs/fullchain.pem` и используется повторно до истечения
срока или смены адреса.

Для публичного домена или публичного IP можно автоматически получить
сертификат Let's Encrypt. В обоих случаях входящий TCP-порт 80 должен быть
доступен удостоверяющему центру, а порт 443 — клиентам. Домен должен указывать
на этот сервер. При NAT настройте переадресацию этих портов на хост Docker.

```sh
scripts/deploy-https.sh up --host chat.example.com \
  --letsencrypt --email admin@example.com

scripts/deploy-https.sh up --host 203.0.113.10 \
  --letsencrypt --email admin@example.com
```

Во втором примере замените документационный IP на свой публичный адрес. Для IP
скрипт запрашивает короткоживущий сертификат через Certbot 5.4. Запускайте
продление ежедневно для любого сертификата Let's Encrypt:

```sh
scripts/deploy-https.sh renew --host chat.example.com
```

Можно добавить эту команду в cron/systemd timer. Для публичного IP укажите в
ней IP вместо домена. Данные Let's Encrypt хранятся в `.https/letsencrypt`;
сохраняйте этот каталог при резервном копировании сервера. Первый выпуск
выполняется через временный самоподписанный сертификат; если выпуск не удался,
nginx останавливается, чтобы не оставлять этот сертификат в работе.
Проверить выпуск через тестовый центр можно флагом `--staging`; его сертификат
не будет доверенным для мобильного приложения.

Скрипт поддерживает `--dry-run` для проверки настроек Compose и переданных
PEM-файлов без запуска контейнеров, копирования сертификата или обращения к
Let's Encrypt. `--no-build` повторно использует имеющийся образ API. Для
нестандартных опубликованных портов и адреса привязки
есть `--http-port`, `--https-port` и `--bind`. Автоматический выпуск Let's
Encrypt требует стандартных публичных портов 80 и 443.

TURN обслуживает звонки по своим TCP/UDP-портам из `compose.yaml`; nginx не
проксирует этот протокол. Для удалённых клиентов отдельно настройте в `.env`
`TURN_URL` и `TURN_EXTERNAL_IP`, а также доступность `3478` и UDP-диапазона
`55000–55039`. Скрипт не меняет сетевые адреса TURN автоматически.

## Отдельный push-шлюз

Развёртывание шлюза, выдача и отзыв токенов описаны в [инструкции push-шлюза](push-gateway/README.md). `install.sh` и `familychat configure-push` принимают `--push-gateway-url https://push.example.com:9443 --push-gateway-token-file /root/family.token`. Установщик проверяет TLS и доступ, подключает `compose.push-gateway.yaml`; только worker получает токен. Ключи APNs/FCM остаются на шлюзе.
