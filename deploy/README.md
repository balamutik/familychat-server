# Установка готового релиза

Пользовательский установщик поддерживает Ubuntu/Debian с systemd и публичным
IPv4. Нужен домен с единственной A-записью на IPv4 VPS, без AAAA и CDN-прокси.
Docker Compose должен быть версии 2.24.4 или новее. При отсутствии Docker
мастер предлагает установить его из официального apt-репозитория Docker.
Firewall провайдера установщик не изменяет: разрешите TCP 80, 443, 3478 и
UDP 3478, 55000–55039. При выпуске сертификата Let's Encrypt проверяет доступ
снаружи; локальная проверка свободных портов не гарантирует доступ через firewall.

После публикации релиза:

```sh
curl -fsSL https://github.com/balamutik/familychat-server/releases/latest/download/install.sh | sudo bash
```

Введите домен и email для сертификата. Авторизация в registry не нужна, если
репозиторий и пакет GHCR публичные. Установка создаёт `/opt/familychat` (0700):
служебный `.env` и состояние (0600), закрытый каталог `secrets`, сертификаты
`.https` и каталоги версий `releases`. API запускается не от root, поэтому
смонтированный файл первого пароля читается контейнером; его каталог на VPS
доступен только root. Пароль не записывается в Git и не входит в релиз.

Команды после установки:

```sh
sudo familychat status                 # версия и состояние контейнеров
sudo familychat logs                   # последние записи и поток журналов
sudo familychat update                 # последний стабильный релиз
sudo familychat update --version v1.0.1 # конкретный опубликованный релиз
sudo familychat renew                  # ручное продление сертификата
```

`familychat-renew.timer` ежедневно запускает продление HTTPS. Состояние таймера:
`systemctl status familychat-renew.timer`. Первые учётные данные показываются
после создания администратора. Исходный пароль хранится в
`/opt/familychat/secrets/admin-password.txt`; после смены пароля в приложении
этот файл не отражает новый пароль.

Обновление запрашивает подтверждение готовности резервной копии. Сохраняйте
согласованную копию PostgreSQL и файлового хранилища, а также `/opt/familychat`
(секреты и сертификаты). Файлы `secrets/content-public-key.txt` и
`secrets/content-private-key.txt` содержат общую пару шифрования и обязательно
входят в резервную копию. Перед переходом с v2.0.0 сохраните также том
`familychat_encryption_keys`: установщик перенесёт из него ту же пару в Docker
secrets. API получит два секрета только для чтения, worker их не получает.
Томам данных всегда назначаются имена
`familychat_postgres_data` и `familychat_s3_data`, независимо от версии релиза.
Данные не входят в образ. Не удаляйте тома через `docker compose down -v`.
Миграции применяются при запуске: выбор старой версии не откатывает схему БД.
При ошибке после начала активации установщик сохраняет номер незавершённого
релиза. Повторите ту же установочную команду или `familychat update` без версии,
чтобы продолжить. Автоматического отката миграций нет.

Старые установки из Git не импортируются автоматически: установщик не
перезаписывает найденные настройки, не использует чужие тома и проверяет
занятость портов. Продолжайте обновлять такую установку прежним способом либо
отдельно перенесите данные и настройки. APNs требует вашего ключа Apple
Developer; мастер его не создаёт. Без APNs чаты и звонки работают при открытом
приложении, фоновые push-уведомления iOS требуют отдельной настройки.

## Выпуск версии владельцем проекта

Workflow `.github/workflows/release.yml` запускается при пуше тега `vX.Y.Z`.
Он проверяет установщик, собирает образ для `linux/amd64` и `linux/arm64`,
публикует его в `ghcr.io/balamutik/familychat-server`, затем создаёт GitHub Release
с `install.sh`, `familychat-server.tar.gz` и `SHA256SUMS`. API, worker и подготовительный key-setup в комплекте
используют один digest образа; исходники, `.env` и секреты туда не входят.
Изменение файлов конфигурации доставляется вместе с новой версией образа.

Первый выпуск после проверки изменений:

```sh
git tag v1.0.0
git push origin v1.0.0
```

Номер версии выбирает владелец. Опубликованные релизы не перезаписываются.
Для доступа других людей владелец отдельно делает публичными репозиторий GitHub
и пакет Container Registry (Package settings → Change visibility → Public).
В приватном репозитории сборка/публикация возможна, но анонимная установка
недоступна. Смена видимости репозитория сама по себе не заменяет проверку
доступности пакета GHCR. Workflow использует встроенный `GITHUB_TOKEN` с правами
`contents: write` и `packages: write`, дополнительных секретов ему не нужно.

Проверки установщика без изменения VPS:

```sh
python3 -m unittest discover -s tests/installer -v
bash -n install.sh scripts/deploy-https.sh
shellcheck install.sh
```

Проверка сгенерированного Compose (не запускает сервисы):

```sh
python3 tests/installer/validate_compose.py /path/to/familychat-server.tar.gz
```
 Полный сценарий
Docker/systemd/Let's Encrypt необходимо проверять на отдельном VPS с DNS;
unit-тесты не подтверждают публичную доступность и работу TURN.

# HTTPS-развёртывание сервера

Команды выполняются из каталога `server`. Сначала заполните `.env` по образцу
`.env.example` и создайте `secrets/admin-password.txt`. Скрипт собирает образы
API и worker, запускает PostgreSQL, хранилище файлов, TURN, API, worker и nginx.
В этом режиме порт API `8080` не публикуется; nginx принимает `80/443` и
проксирует **все HTTP-маршруты**, включая `/admin/`, API, WebSocket и файлы.

Для сертификата и ключа в формате PEM:

```sh
scripts/deploy-https.sh up --host chat.example.com \
  --cert /path/to/fullchain.pem --key /path/to/privkey.pem
```

Сертификат должен содержать выбранный DNS-адрес или IP в Subject Alternative
Name. Файлы копируются в игнорируемый Git каталог `.https/certs`, поэтому
исходные PEM-файлы должны оставаться доступными только администратору.

Для тестирования на собственном IP, например в локальной сети:

```sh
scripts/deploy-https.sh up --host 192.168.1.20 --self-signed
```

Самоподписанный сертификат нужно добавить в доверенные на каждом клиентском
устройстве; иначе приложение не установит HTTPS-соединение. Сертификат
сохраняется в `.https/certs/fullchain.pem` и используется повторно до истечения
срока или смены адреса.

Для публичного домена или публичного IP можно автоматически получить
сертификат Let's Encrypt. В обоих случаях входящий TCP-порт 80 должен быть
доступен удостоверяющему центру, а порт 443 — клиентам. Домен должен указывать
на этот сервер. При NAT настройте переадресацию этих портов на хост Docker.

```sh
scripts/deploy-https.sh up --host chat.example.com \
  --letsencrypt --email admin@example.com

scripts/deploy-https.sh up --host 203.0.113.10 \
  --letsencrypt --email admin@example.com
```

Во втором примере замените документационный IP на свой публичный адрес. Для IP
скрипт запрашивает короткоживущий сертификат через Certbot 5.4. Запускайте
продление ежедневно для любого сертификата Let's Encrypt:

```sh
scripts/deploy-https.sh renew --host chat.example.com
```

Можно добавить эту команду в cron/systemd timer. Для публичного IP укажите в
ней IP вместо домена. Данные Let's Encrypt хранятся в `.https/letsencrypt`;
сохраняйте этот каталог при резервном копировании сервера. Первый выпуск
выполняется через временный самоподписанный сертификат; если выпуск не удался,
nginx останавливается, чтобы не оставлять этот сертификат в работе.
Проверить выпуск через тестовый центр можно флагом `--staging`; его сертификат
не будет доверенным для мобильного приложения.

Скрипт поддерживает `--dry-run` для проверки настроек Compose и переданных
PEM-файлов без запуска контейнеров, копирования сертификата или обращения к
Let's Encrypt. `--no-build` повторно использует имеющийся образ API. Для
нестандартных опубликованных портов и адреса привязки
есть `--http-port`, `--https-port` и `--bind`. Автоматический выпуск Let's
Encrypt требует стандартных публичных портов 80 и 443.

TURN обслуживает звонки по своим TCP/UDP-портам из `compose.yaml`; nginx не
проксирует этот протокол. Для удалённых клиентов отдельно настройте в `.env`
`TURN_URL` и `TURN_EXTERNAL_IP`, а также доступность `3478` и UDP-диапазона
`55000–55039`. Скрипт не меняет сетевые адреса TURN автоматически.
