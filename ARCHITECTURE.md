# FamilyChat: сервер первой версии

Статус: спецификация согласована; подготовлен план реализации, код ещё не написан.
Дата: 2026-09-29.

## Назначение и согласованные требования

Домашний мессенджер с личными и групповыми чатами, серверной историей,
поиском, фотографиями, видео, документами и произвольными файлами.
Для фото и видео клиент получает превью. Голосовые и видеозвонки — только
между двумя пользователями; это ограничение подтверждено пользователем.
Вход по логину и паролю. Самостоятельная регистрация означает, что пользователь
сам создаёт аккаунт с логином и паролем, если администратор разрешил регистрацию.
Используется S3-совместимое хранилище. Развёртывание в Docker.
На этом этапе работа ограничена каталогом `server`; клиент мессенджера не разрабатывается.
Язык сервера — Go, выбран пользователем.
В состав решения входит административная панель на React.
Все запросы содержимого файлов к серверу требуют заголовка авторизации,
включая оригиналы, фото, видео, документы и превью.

## Предлагаемые решения

Следующие пункты являются предложениями, а не дополнительными требованиями пользователя:

- Сообщения, аккаунты, членство в чатах и служебные записи хранятся в PostgreSQL.
  S3 хранит исходные вложения и превью. Такое разделение обеспечивает транзакции,
  контроль доступа и индексируемый поиск по истории.
- Сервер — модульный монолит на Go со стандартным `net/http` для HTTP API.
  API, worker и служебные команды используют общий Go-модуль и слой доступа к PostgreSQL.
- Административная панель — React + TypeScript в `server/admin`.
  Собранная статика обслуживается Go-сервером по `/admin/` с того же origin, что и API.
- Один экземпляр API для домашнего использования; REST для операций,
  WebSocket для событий и сигнализации звонков. Отдельный процесс worker из того же образа
  создаёт превью и очищает незавершённые загрузки.
- Docker Compose объединяет API, worker, PostgreSQL и coturn.
  S3 может быть внешним; для локального запуска предусматривается отдельный профиль
  с S3-совместимым хранилищем. Данные сохраняются в постоянных томах / бакете.

### Рассмотренные подходы

1. **Собственный модульный монолит — предлагаемый вариант.** Позволяет точно задать API
   для будущего клиента, регистрацию и файловое хранилище при небольшом числе компонентов.
2. **Готовый сервер протокола обмена сообщениями.** Сокращает часть разработки,
   но привязывает клиент, администрирование и хранение к чужой модели.
3. **Набор микросервисов.** Даёт независимое масштабирование, но усложняет эксплуатацию
   домашнего приложения; для первой версии преимуществ недостаточно.

## Аккаунты и доступ

- Роли сервера: `admin`, `user`; роли группы: `owner`, `admin`, `member`.
- Первый администратор создаётся отдельной командой bootstrap с безопасным вводом пароля.
  Первый зарегистрировавшийся пользователь не получает административные права.
- Самостоятельная регистрация по умолчанию выключена; администратор может включить её
  и создавать пользователей независимо от этого переключателя.
- Логины уникальны без учёта регистра. Пароли хешируются Argon2id; ввод и попытки
  регистрации/входа ограничиваются по размеру и частоте. Ошибки входа не раскрывают,
  существует ли логин.
- Сессии имеют криптографически случайные токены; в БД сохраняется только хеш токена.
  Logout, смена пароля и блокировка аккаунта отзывают соответствующие сессии.
- REST использует Bearer-токен. Для WebSocket REST выдаёт короткоживущий одноразовый
  билет: основной токен не передаётся в URL. Origin проверяется по списку разрешённых.
- Каждая операция с сообщением, вложением, поиском, событием или звонком проверяет
  текущую сессию и право пользователя на конкретный объект.
- Административная роль сама по себе не даёт API-доступ к чужим чатам.
  Серверное хранение не является сквозным шифрованием сообщений.

## Административная панель

- Панель на React входит в первую версию: вход по логину и паролю, выход,
  список пользователей с поиском и пагинацией, создание аккаунта,
  блокировка и разблокировка пользователей, переключатель самостоятельной регистрации.
- Панель использует `/api/v1/admin/*`. Каждый административный запрос требует
  `Authorization: Bearer <session_token>` и серверной проверки роли `admin`.
  Скрытие элементов интерфейса не заменяет проверку прав в Go API.
- Обычный пользователь получает `403` на административные операции;
  отсутствие, истечение или отзыв сессии — `401`. Панель показывает отказ в доступе
  либо возвращает на экран входа, очищая данные предыдущего пользователя.
- Блокировка немедленно отзывает сессии и отключает активные WebSocket-подключения;
  разблокировка не восстанавливает отозванные сессии. Последнего активного
  администратора заблокировать нельзя; это проверяется атомарно на сервере.
- Изменения отображаются как сохранённые только после успешного ответа API.
  Есть состояния загрузки, пустого списка и ошибки; неудача сохранения настройки
  не показывает пользователю ложное успешное переключение регистрации.
- Сессионный токен панели хранится в памяти приложения и передаётся общим API-клиентом
  только на свой origin. После перезагрузки страницы требуется повторный вход.
  Logout и `401` очищают токен, данные и отменяют незавершённые запросы;
  поздний ответ от предыдущей сессии не должен восстановить её данные в интерфейсе.
- Панель не предоставляет просмотр содержимого чужих чатов и файлов.
  Статические HTML/JS/CSS панели доступны для загрузки экрана входа;
  обязательная авторизация файлов относится к пользовательским вложениям и их превью.

## Чаты, сообщения и синхронизация

- Для неупорядоченной пары пользователей существует не более одного личного чата.
- Создатель группы становится владельцем; он назначает администраторов и передаёт
  владение. Последний владелец не может выйти без передачи владения или удаления группы.
- Владелец и администраторы управляют составом группы. Участник может выйти.
  Предлагаемое правило: новый участник получает всю историю; вышедший или исключённый
  теряет серверный доступ к истории, поиску, вложениям и новым событиям.
- Сообщение содержит текст и/или вложения. Вложения принадлежат тому же чату
  и загрузившему их отправителю; чужие идентификаторы нельзя присоединить к сообщению.
- `client_message_id` обеспечивает идемпотентность повторной отправки.
  Подтверждение отправки возвращается после фиксации транзакции PostgreSQL.
- Сервер назначает сообщение и последовательный номер внутри чата, время UTC.
  История читается по курсору, с ограничением размера страницы.
- Сообщение и запись события сохраняются одной транзакцией. WebSocket ускоряет доставку,
  а после разрыва клиент восстанавливает историю через REST по последнему номеру.
  Повторные события допускаются и устраняются клиентом по идентификаторам.
- Предусмотрен монотонный указатель прочитанного сообщения участника, чтобы клиент
  мог показывать непрочитанные сообщения и подтверждения чтения.
- В первой версии не предполагаются каналы, боты, истории и другие неуказанные
  функции Telegram. Редактирование и удаление отдельных сообщений — последующее расширение.

## Файлы и превью

- Бакет приватный. Приложение генерирует непрозрачные ключи объектов;
  имена пользовательских файлов не используются как пути.
- Для первой версии загрузка проходит потоком через API в S3, с ограничением размера,
  таймаутом и квотой пользователя. Файл не буферизуется целиком в памяти.
  Предлагаемые начальные лимиты: 250 МиБ на файл, 10 ГиБ на пользователя;
  значения изменяются конфигурацией.
- API сначала проверяет членство, резервирует квоту в БД, записывает объект под новым
  ключом, затем фиксирует метаданные. При ошибке освобождает резерв; оставшиеся объекты
  удаляются повторяемой фоновой задачей. Активные загрузки имеют срок действия.
- В сообщении может использоваться только полностью загруженный объект.
  Исходный объект после завершения загрузки не перезаписывается клиентом.
- Worker определяет тип содержимого и создаёт уменьшенную картинку для поддерживаемых
  изображений и кадр-превью для поддерживаемых видео. Для видео используется FFmpeg.
  Поддержка декодирования ограничена явно документированными форматами;
  неизвестный формат остаётся доступным как обычный файл.
- Задания превью находятся в PostgreSQL, имеют lease, таймаут, ограниченное число
  повторов и состояния `pending`, `processing`, `ready`, `failed`, `unsupported`.
  Worker ограничен по памяти, CPU, времени декодирования, размеру кадра и параллелизму.
- Неудача создания превью не теряет исходник. API возвращает статус и метаданные:
  имя, размер, MIME, размеры изображения/видео и длительность, когда они доступны.
- Скачивание и превью проходят через Go API, который проверяет права и передаёт поток
  из приватного S3. Клиент не получает публичных или подписанных S3-ссылок,
  а API не перенаправляет его в S3. Серверные S3-реквизиты не передаются клиенту.
- Каждый `GET` и `HEAD` оригинала или превью требует
  `Authorization: Bearer <session_token>`. Это относится и к повторным,
  условным запросам и каждому запросу диапазона с `Range`.
  Токен в query string или cookie без заголовка не заменяет этот заголовок.
- До чтения из S3 и выдачи метаданных API проверяет сессию и доступ к вложению:
  действующее членство в чате и связь файла с доступным сообщением.
  До отправки сообщения полностью загруженный файл доступен только загрузившему
  его пользователю, пока тот остаётся участником чата.
- При отсутствии или недействительности токена возвращается `401`;
  для недоступного либо несуществующего вложения — одинаковый `404`.
  Ответ на `HEAD` всегда без тела. Проверка доступа выполняется до обработки
  условных запросов и диапазонов, чтобы ошибки и `304` не раскрывали метаданные.
- Поддерживается HTTP Range для видео: `Accept-Ranges: bytes`, `206`,
  `Content-Range` и `416` для недопустимого диапазона. Каждый диапазон проходит
  полную проверку доступа. Ответы файлов и ошибки содержат `Cache-Control: private, no-store`;
  reverse proxy не должен кэшировать их и обходить авторизацию.
- После исключения из чата или отзыва сессии следующий запрос, включая Range,
  отклоняется. Уже переданные клиенту байты отозвать невозможно;
  открытый поток не считается новым запросом при получении каждого байта.
- В production панель работает на одном origin с API. Если разрешён отдельный origin
  разработки, CORS допускает только настроенные origin, заголовки `Authorization`,
  `Range`, `Content-Type` и чтение `Content-Range`, `Accept-Ranges`, `Content-Disposition`.
  Preflight `OPTIONS` не требует сессии, но не выдаёт содержимое и сведения о файле.
- Неподдерживаемые и потенциально исполняемые файлы выдаются как вложения;
  заголовки исключают автоматическое определение типа браузером.

### Контракт для клиентов медиа

- API возвращает защищённые относительные пути к оригиналу и превью, без секретов в URL.
  Фото и превью в браузерном клиенте загружаются через `fetch` с `Authorization`,
  затем отображаются через локальный Blob URL. При замене изображения, выходе
  и размонтировании компонента Blob URL освобождается, незавершённая загрузка отменяется.
- Простая установка серверного URL в `img.src`, `video.src` или ссылку скачивания
  не обеспечивает отправку Bearer-заголовка. Будущий клиент должен использовать
  загрузчик с поддержкой заголовков; видео — с авторизованными Range-запросами,
  без обязательного скачивания всего большого файла в Blob перед воспроизведением.
  Реализация проигрывателя относится к клиенту мессенджера и проверяется отдельно.
- Контракт скачивания одинаков для браузерных и мобильных клиентов:
  доступ определяется сессией и правами, а знание URL не предоставляет доступа.

## Поиск

- Поиск внутри указанного чата по тексту сообщений, подписям и именам файлов.
- PostgreSQL Full Text Search для русского текста, дополненный индексом для поиска
  фрагментов и имён файлов. Запросы параметризованы, длина и выдача ограничены.
- Проверка членства выполняется до выдачи результатов и применяется к SQL-запросу.
  Курсор использует стабильный порядок. Содержимое документов и OCR не индексируются.

## Звонки один на один

- Сервер создаёт звонок для двух участников личного чата; тип `audio` или `video`.
- Состояния: `ringing`, `accepted`, `ended`, `rejected`, `missed`, `cancelled`.
  Принятие возможно только вызываемым пользователем; завершение — участниками.
  Переходы атомарны, повторные команды идемпотентны. Таймаут ответа — 45 секунд.
- Одновременный активный звонок пользователя только один; конкурирующие вызовы
  возвращают `busy`. При нескольких устройствах первое принятие выигрывает,
  остальные получают событие остановки звонка.
- SDP и ICE передаются через авторизованный WebSocket только между выбранными
  устройствами участников активного звонка. Сервер ограничивает размер и частоту
  сигналов; SDP/ICE и токены не попадают в обычные логи.
- Медиа передаётся между клиентами через WebRTC. coturn обеспечивает STUN/TURN
  для соединений, которым нужен ретранслятор. Групповой медиасервер не требуется.
- Авторизованный участник получает временные TURN-реквизиты для активного звонка,
  с обновлением для долгого разговора. Постоянный секрет TURN остаётся на сервере.
  TURN настраивается с запретом ретрансляции в приватные/служебные сети и с квотами.
- В PostgreSQL сохраняются участники, тип, время и итог звонка. Медиа не записывается.
  Перезапуск сервера завершает оставшиеся активные звонки с причиной `server_restart`.
- При потере сигнализации клиенту даётся ограниченное окно переподключения;
  после истечения 30 секунд сервер завершает звонок и уведомляет второго участника.
- Фоновый входящий звонок на спящем телефоне требует интеграции клиента с APNs/FCM
  и системным интерфейсом звонков. Без неё первая версия гарантирует сигнализацию
  только при активном подключении клиента; интеграция push требует отдельной настройки.

## Основные интерфейсы

Все API-интерфейсы версионируются префиксом `/api/v1` и документируются OpenAPI.
Панель обслуживается отдельно по `/admin/`; SPA fallback применяется только к её маршрутам
и не подменяет ответы ошибок API или защищённых файлов страницей HTML.

| Область | Операции |
| --- | --- |
| Auth | register, login, logout, me, change-password, websocket-ticket |
| Admin | настройка регистрации, список и создание пользователей, блокировка и разблокировка |
| Users | поиск по логину среди активных аккаунтов для начала личного чата |
| Chats | список, личный чат, создание группы, информация, состав и роли, выход |
| Messages | отправка, постраничная история, восстановление после курсора, прочтение |
| Files | потоковая загрузка, статус, оригинал и превью; обязательный Authorization, GET/HEAD/Range |
| Search | поиск в доступном чате |
| Calls | начать, принять, отклонить, отменить, завершить, состояние, TURN-реквизиты |
| WebSocket | новые сообщения, прочтение, изменения чатов/вложений, звонки и сигнализация |
| Operations | liveness, readiness |

Основные таблицы: `users`, `sessions`, `settings`, `chats`, `chat_members`,
`messages`, `attachments`, `message_attachments`, `upload_reservations`,
`preview_jobs`, `events`, `calls`. Ограничения уникальности и внешние ключи
обеспечивают целостность независимо от логики HTTP-обработчиков.

## Эксплуатация

- Многостадийная сборка Docker; процессы работают без root. Версии зависимостей
  закреплены в `go.mod`, контрольные суммы — в `go.sum`.
  Версии Go и образов фиксируются при реализации.
- Отдельная стадия Docker собирает React-панель; её артефакты входят в образ Go API.
  Node.js нужен только при сборке. Зависимости панели закрепляются npm lock-файлом;
  установка в CI и Docker выполняется через `npm ci`.
- Миграции БД — отдельная команда, выполняемая до запуска API/worker.
  Readiness проверяет доступность PostgreSQL, S3 и совместимость схемы.
- TLS завершается на reverse proxy; для TURN документируются публичный адрес,
  порты UDP/TCP, диапазон реле и поведение за NAT. Секреты не хранятся в Git.
- Логи структурированные, с идентификатором запроса, без паролей, токенов и текстов сообщений.
- Резервное копирование включает PostgreSQL и S3; одного бакета для восстановления
  пользователей, истории и связей недостаточно. В README будет процедура восстановления.

## Приёмка реализации

1. Docker Compose запускает зависимости, миграции, API и worker; healthchecks проходят.
2. Bootstrap создаёт администратора. Переключатель регистрации реально разрешает
   и запрещает регистрацию; роли обычного пользователя не позволяют его менять.
3. Два клиента обмениваются сообщениями; после рестарта и переподключения история
   восстанавливается. Повторная отправка с тем же `client_message_id` не дублируется.
4. Создание группы, добавление, выход и исключение работают. Посторонний и исключённый
   не читают сообщения, поиск, файлы, превью и WebSocket-события группы.
5. Фото, видео, документ и произвольный файл проходят реальный цикл загрузки в S3,
   отправки и скачивания. Фото/видео поддерживаемых форматов получают реальные превью.
   Проверяются Range, лимит размера, ошибка декодирования и очистка незавершённой загрузки.
6. Поиск находит русские сообщения и имена файлов; выдача ограничена нужным чатом.
7. Проверяются переходы звонка, таймаут, busy, гонка принятия на двух устройствах,
   запрет чужой сигнализации и истечение TURN-реквизитов.
8. Два тестовых браузерных клиента устанавливают аудио/видео WebRTC-соединение,
   включая принудительный TURN relay. Проверка между разными реальными сетями
   фиксируется отдельно; успешные тесты сигнализации не подтверждают передачу медиа.
9. Проверяется форматирование `gofmt`; выполняются `go vet ./...`,
   `go test -race ./...` и `go build ./...`, включая интеграционные сценарии
   с PostgreSQL/S3. Неисполненные live-проверки явно указываются.
10. На реальном маршруте `/admin/` проверяются вход администратора, создание,
    блокировка/разблокировка пользователя и изменение регистрации.
    Изменения сохраняются после перезапуска; обычный пользователь не получает доступ
    к административным данным даже прямыми запросами API. Проверяются отказ API,
    очистка данных при выходе и запрет блокировки последнего администратора.
11. Для оригинала, превью, `HEAD`, условных и Range-запросов проверяются:
    валидный токен участника, отсутствие заголовка, истёкшая/отозванная сессия,
    чужой аккаунт, исключённый участник, токен только в URL или cookie.
    Отказы не раскрывают файл или его метаданные; редиректов на S3 нет.
    Реальная браузерная загрузка превью и тестовый Range-запрос передают Authorization.
12. Панель проходит проверку TypeScript, lint, production build и браузерные тесты
    административных сценариев. Docker-образ обслуживает её вместе с Go API.
