# FamilyChat server

Домашний чат на Go: личные и групповые чаты, история и поиск, файлы в приватном S3, превью изображений и видео, события по WebSocket и звонки один на один через WebRTC/TURN. Административная панель написана на React и открывается по `/admin/`.

## Локальный запуск

Нужны Docker Compose и открытые порты `8080/tcp`, `3478/tcp+udp`, `55000–55039/udp`. Создайте настройки и пароль первого администратора:

```sh
cp .env.example .env
# Замените POSTGRES_PASSWORD, S3_ACCESS_KEY, S3_SECRET_KEY и TURN_SECRET
mkdir -p secrets
printf '%s\n' 'длинный-случайный-пароль-администратора' > secrets/admin-password.txt
chmod 600 .env secrets/admin-password.txt
docker compose up -d --build
docker compose run --rm api bootstrap-admin
```

Команда `bootstrap-admin` допускает ровно одно создание первого администратора. Логин по умолчанию `admin`; его можно изменить через `ADMIN_LOGIN` в Compose. Пароль считывается только из `secrets/admin-password.txt`. Файлы `.env` и `secrets/` исключены из Git. Панель: `http://localhost:8080/admin/`. Самостоятельная регистрация **выключена** до включения администратором. Она позволяет создать аккаунт с обязательными логином и паролем без телефона, почты и приглашения; гостевого доступа нет.

В разделе «Хранение» администратор задаёт `retention_days` (0 — бессрочно, максимум 3650 дней) и `max_file_bytes`. Срок отсчитывается от загрузки и действует на вложения чатов, включая уже загруженные: после истечения срока оригинал и превью сразу перестают выдаваться API, worker удаляет их из S3, а сообщение с пометкой `available: false` остаётся в истории. Аватар профиля хранится до замены или удаления владельцем. Увеличение срока после удаления вложения не восстанавливает файл. Размер ограничивает новые загрузки; верхний предел задаётся `MAX_FILE_BYTES` в `.env` (по умолчанию 250 МиБ) и требует перезапуска контейнеров для изменения. `USER_QUOTA_BYTES` должен быть не меньше этого предела. Для медиа размером свыше 250 МиБ worker может не создать превью, но исходник останется доступен до истечения срока.

Для внешнего доступа завершайте TLS на reverse proxy, используйте HTTPS/WSS, укажите домен в `ALLOWED_ORIGINS` и ограничьте доступ к внутренним PostgreSQL/S3. S3-порт в Compose не опубликован, а API по умолчанию привязан только к `127.0.0.1:8080`. Для звонков замените `TURN_URL` и `TURN_EXTERNAL_IP` на публичный адрес coturn, откройте relay-диапазон UDP и при NAT настройте отображение внутреннего/внешнего адреса под свою сеть. Значение `127.0.0.1` предназначено только для локальной проверки. Доступность звонков между разными сетями зависит от этой сетевой настройки. Push-уведомления о звонках в спящем мобильном приложении не входят в эту версию.

## Авторизация и файлы

`POST /api/v1/auth/login` принимает `{"login":"…","password":"…"}` и возвращает случайный Bearer-токен. Все операции с чатами, сообщениями, файлами и звонками требуют `Authorization: Bearer <token>`. Токен хранится сервером только в виде SHA-256 и отзывается при выходе, блокировке аккаунта или смене пароля. В админке токен остаётся в памяти вкладки.

Файл загружается **через API**, привязывается к конкретному чату и после отправки сообщения доступен его текущим участникам. До отправки его видит только загрузивший участник. Исключённый участник и посторонний администратор не получают ни оригинал, ни превью; при запросе выдаётся `404`. Отсутствие Bearer даёт `401`. Скачивание никогда не перенаправляет на S3 и не создаёт публичную ссылку. Пример:

```sh
curl -X POST "http://localhost:8080/api/v1/chats/$CHAT_ID/files" \
  -H "Authorization: Bearer $TOKEN" \
  -H 'X-File-Name: photo.jpg' -H 'Content-Type: image/jpeg' \
  --data-binary @photo.jpg

curl "http://localhost:8080/api/v1/files/$FILE_ID/content" \
  -H "Authorization: Bearer $TOKEN" -H 'Range: bytes=0-1023' \
  -o photo-part.bin
```

Клиент ищет собеседника через `GET /api/v1/users?q=логин`, получает его UUID и создаёт личный чат через `/api/v1/chats/direct`. Список личных чатов возвращает логин собеседника в `title` и его публичный `avatar_url`, если аватар есть; `GET /api/v1/chats/{id}/members` возвращает состав группы и аватары участников.

`POST /api/v1/chats/{id}/messages` принимает `client_message_id` (UUID), `text` и `attachment_ids`. История возвращает метаданные вложений: `id`, `content_type`, `preview_state`; клиент формирует адреса `/api/v1/files/{id}/content` и `/preview` и отправляет Bearer при **каждом** запросе, включая загрузку превью и Range. Обычный HTML `<img src>` не добавляет Bearer: web-клиент должен получить `Blob` через `fetch` с заголовком авторизации и использовать локальный object URL, затем освободить его при закрытии экрана.

Аватар — отдельное изображение профиля, не вложение чата. Пользователь отправляет сырой JPEG или PNG через `PUT /api/v1/users/me/avatar` с Bearer, `Content-Type` и `Content-Length`; лимит — 5 МиБ либо меньший установленный лимит файла, размер учитывается в пользовательской квоте. Ответ содержит `avatar_url`. Он также появляется в данных текущего аккаунта, поиске пользователей и списке участников чата. `GET` и `HEAD /api/v1/users/{userID}/avatar` доступны без авторизации, поэтому этот URL можно использовать прямо в `<img>`. Сервер проверяет формат и размеры изображения, не выдаёт ссылку на S3; прочие файлы остаются закрытыми. `DELETE /api/v1/users/me/avatar` удаляет текущий аватар, а worker очищает старый объект после замены или удаления.

Для отметок сообщения клиент явно подтверждает получение через `POST /api/v1/chats/{id}/delivered` с `{"seq": N}` и просмотр через `POST /api/v1/chats/{id}/read` с тем же телом. Просмотр также подтверждает доставку. Указатели монотонны и ограничены последним сообщением чата. Ответ содержит `delivered_seq` и `read_seq`; WebSocket-событие `receipt` содержит их вместе с `user_id`. Каждое сообщение в ответах истории, поиска и отправки содержит `receipts` по текущим получателям, вступившим до отправки, и `delivery` со счётчиками и общим статусом `sent`, `delivered` или `read`. В группе общий статус `delivered`/`read` означает подтверждение **всеми** такими получателями; частичные подтверждения видны в счётчиках и `receipts`. Сам факт отправки на сервер не считается доставкой устройству.

## События и звонки

Клиент получает одноразовый билет через `POST /api/v1/auth/websocket-ticket` с Bearer, затем соединяется с `/api/v1/ws?ticket=…`. Билет живёт 30 секунд и расходуется один раз. Команда `{"type":"sync","after_event_id":123}` повторяет доступные события; после разрыва источником истины остаётся REST-история. Соединение закрывается при отзыве сессии или исключении из чата.

В личном чате `POST /api/v1/chats/{id}/calls` с `{"kind":"audio"}` либо `video` создаёт звонок. Вызываемый пользователь отвечает через `/api/v1/calls/{id}/accept` или `/reject`; звонящий отменяет через `/cancel`, участники завершают `/end`. Отвечает первое устройство, остальные получают конфликт. После принятия выбранные сессии обмениваются по WebSocket кадрами `{"type":"offer|answer|ice","call_id":"…","data":{…}}`. SDP/ICE не сохраняются в истории. `GET /api/v1/calls/{id}/ice` выдаёт выбранному устройству временные TURN-реквизиты на 10 минут; клиент обновляет их во время долгого звонка. Сам медиапоток передаётся WebRTC, не через сервер чата.

## Данные и обслуживание

PostgreSQL хранит сообщения, членство, сессии, события и задания; SeaweedFS в профиле Compose предоставляет приватный S3-совместимый бакет. Worker создаёт JPEG-превью FFmpeg, очищает истёкшие незавершённые загрузки и удаляет файлы по сроку хранения. Резервирование квоты учитывает одновременно загружаемые файлы. При ошибке превью оригинал остаётся доступным.

Резервируйте **вместе** тома `postgres_data` и `s3_data`, иначе ссылки на объекты потеряют соответствие. Для резервной копии PostgreSQL используйте `pg_dump` внутри контейнера и штатные средства резервирования SeaweedFS для тома S3. Перед восстановлением остановите API и worker; восстанавливайте согласованную пару снимков, затем запускайте сервисы и проверяйте `/health/ready` и выборочное скачивание.

Общий контракт API находится в [OpenAPI](api/openapi.yaml). Для мобильного приложения используйте [подробную спецификацию](api/mobile-openapi.yaml): в ней описаны типизированные запросы и ответы пользовательских методов, статусы ошибок, защищённая загрузка файлов и Range-проигрывание видео, а также кадры WebSocket в расширении `x-websocket-messages`. Административные методы в мобильный контракт не входят. Проверки разработчика:

```sh
go test ./...
go vet ./...
cd admin && npm ci && npm run build
docker compose config -q
python3 tests/integration/live_compose.py
python3 tests/integration/turn_probe.py
```

Первые три проверки работают без внешних сервисов; Go-интеграционные тесты используют `TEST_DATABASE_URL`, `TEST_S3_ENDPOINT`, `TEST_S3_ACCESS_KEY` и `TEST_S3_SECRET_KEY` для отдельной тестовой базы и бакета `familychat-test`. Два Python-сценария проверяют уже запущенный Compose; `live_compose.py` создаёт тестовые аккаунты и сообщения в его локальной базе.
