# FamilyChat server

Домашний чат на Go: личные и групповые чаты, история и поиск, файлы в приватном S3, превью изображений и видео, события по WebSocket и звонки один на один через WebRTC/TURN. Административная панель написана на React и открывается по `/admin/`.

## Установка на VPS одной командой

После публикации первого стабильного релиза и открытия доступа к репозиторию и
образу GHCR пользователь запускает на Ubuntu/Debian VPS:

```sh
curl -fsSL https://github.com/balamutik/familychat-server/releases/latest/download/install.sh | sudo bash
```

Установщик спрашивает домен и email для HTTPS, предлагает установить Docker,
генерирует секреты, скачивает готовые образы, создаёт первого администратора и
включает ежедневное продление сертификата. В конце показывает адрес админки и
первый пароль. Редактировать `.env` или Compose не нужно.

Для первого выпуска нужен публичный IPv4, домен с A-записью на этот VPS без
CDN-проксирования и AAAA-записи, свободные TCP 80/443/3478 и UDP 3478/55000–55039.
Эти порты нужно разрешить и в firewall провайдера. Подробности установки,
обновления и выпуска релизов — в [инструкции развёртывания](deploy/README.md).

```sh
sudo familychat status
sudo familychat logs
sudo familychat update
```

Повторный запуск установщика сохраняет настройки и пароль. Автоматический
перенос существующей ручной установки не выполняется: для неё сохраняется
описанный ниже способ запуска.

## Локальный запуск

Нужны Docker Compose и открытые порты `8080/tcp`, `3478/tcp+udp`, `55000–55039/udp`. Создайте настройки и пароль первого администратора:

```sh
cp .env.example .env
# Замените POSTGRES_PASSWORD, S3_ACCESS_KEY, S3_SECRET_KEY и TURN_SECRET
mkdir -p secrets
printf '%s\n' 'длинный-случайный-пароль-администратора' > secrets/admin-password.txt
chmod 700 secrets
chmod 600 .env
chmod 644 secrets/admin-password.txt
docker compose run --rm --build key-setup
docker compose up -d --build
docker compose run --rm api bootstrap-admin
```

Команда `bootstrap-admin` допускает ровно одно создание первого администратора. Логин по умолчанию `admin`; его можно изменить через `ADMIN_LOGIN` в Compose. Пароль считывается только из `secrets/admin-password.txt`. Файлы `.env` и `secrets/` исключены из Git. Панель: `http://localhost:8080/admin/`. Самостоятельная регистрация **выключена** до включения администратором. Она позволяет создать аккаунт с обязательными логином и паролем без телефона, почты и приглашения; гостевого доступа нет.

В разделе «Хранение» администратор задаёт `retention_days` (0 — бессрочно, максимум 3650 дней) и `max_file_bytes`. Срок отсчитывается от загрузки и действует на вложения чатов, включая уже загруженные: после истечения срока оригинал и превью сразу перестают выдаваться API, worker удаляет их из S3, а сообщение с пометкой `available: false` остаётся в истории. Аватар профиля хранится до замены или удаления владельцем. Увеличение срока после удаления вложения не восстанавливает файл. Размер ограничивает новые загрузки; верхний предел задаётся `MAX_FILE_BYTES` в `.env` (по умолчанию 250 МиБ) и требует перезапуска контейнеров для изменения. `USER_QUOTA_BYTES` должен быть не меньше этого предела. Для медиа размером свыше 250 МиБ worker может не создать превью, но исходник останется доступен до истечения срока.

Для внешнего доступа завершайте TLS на reverse proxy, используйте HTTPS/WSS, укажите домен в `ALLOWED_ORIGINS` и ограничьте доступ к внутренним PostgreSQL/S3. S3-порт в Compose не опубликован, а API по умолчанию привязан только к `127.0.0.1:8080`. Для звонков замените `TURN_URL` и `TURN_EXTERNAL_IP` на публичный адрес coturn, откройте relay-диапазон UDP и при NAT настройте отображение внутреннего/внешнего адреса под свою сеть. Значение `127.0.0.1` предназначено только для локальной проверки. Доступность звонков между разными сетями зависит от этой сетевой настройки.

Для временной проверки с iPhone в той же Wi-Fi-сети укажите в `.env`: `API_BIND_HOST=192.168.0.15`, `TURN_URL=turn:192.168.0.15:3478?transport=udp`, `TURN_EXTERNAL_IP=192.168.0.15` и `ALLOWED_ORIGINS=localhost,192.168.0.15`. Подставьте актуальный LAN-IP Mac и добавьте сервер в приложении как `http://192.168.0.15:8080`. При смене IP обновите адреса в `.env` и перезапустите контейнеры. Админ-панель также будет доступна по `http://192.168.0.15:8080/admin/`.

## Авторизация и файлы

`POST /api/v1/auth/login` принимает `{"login":"…","password":"…"}` и возвращает случайный Bearer-токен. Все операции с чатами, сообщениями, файлами и звонками требуют `Authorization: Bearer <token>`. Токен хранится сервером только в виде SHA-256 и отзывается при выходе, блокировке аккаунта или смене пароля. В админке токен остаётся в памяти вкладки.

Файл загружается **через API**, привязывается к конкретному чату и после отправки сообщения доступен его текущим участникам. До отправки его видит только загрузивший участник. Исключённый участник и посторонний администратор не получают ни оригинал, ни превью; при запросе выдаётся `404`. Отсутствие Bearer даёт `401`. Скачивание никогда не перенаправляет на S3 и не создаёт публичную ссылку. Пример:

```sh
curl -X POST "http://localhost:8080/api/v1/chats/$CHAT_ID/files" \
  -H "Authorization: Bearer $TOKEN" \
  -H 'X-File-Name: photo.jpg' -H 'Content-Type: image/jpeg' \
  --data-binary @photo.jpg

curl "http://localhost:8080/api/v1/files/$FILE_ID/content" \
  -H "Authorization: Bearer $TOKEN" -H 'Range: bytes=0-1023' \
  -o photo-part.bin
```

Клиент ищет собеседника через `GET /api/v1/users?q=логин`, получает его UUID и создаёт личный чат через `/api/v1/chats/direct`. Список личных чатов возвращает логин собеседника в `title` и его публичный `avatar_url`, если аватар есть; `GET /api/v1/chats/{id}/members` возвращает состав группы и аватары участников.

`POST /api/v1/chats/{id}/messages` принимает `client_message_id` (UUID), `text` и `attachment_ids`. История возвращает метаданные вложений: `id`, `content_type`, `preview_state`; клиент формирует адреса `/api/v1/files/{id}/content` и `/preview` и отправляет Bearer при **каждом** запросе, включая загрузку превью и Range. Обычный HTML `<img src>` не добавляет Bearer: web-клиент должен получить `Blob` через `fetch` с заголовком авторизации и использовать локальный object URL, затем освободить его при закрытии экрана.

Загруженный файл можно прикрепить к сообщению в течение суток. Если за это время сообщение не создано, worker удаляет оригинал и превью и освобождает квоту даже при бессрочном хранении сообщений (`retention_days=0`).

Превью новых зашифрованных изображений (включая HEIC) и видео создаются на устройстве, шифруются и загружаются отдельно. Старые готовые превью шифруются при миграции; worker не обрабатывает зашифрованные оригиналы. Превью, как и оригиналы, выдаются только участникам чата через API.

Аватар — отдельное изображение профиля, не вложение чата. Пользователь отправляет JPEG, PNG/APNG, GIF, WebP, HEIC/HEIF, AVIF, BMP, TIFF, ICO или SVG через `PUT /api/v1/users/me/avatar` с Bearer, `Content-Type` и `Content-Length`; лимит входного файла — 5 МиБ либо меньший установленный лимит файла. JPEG и PNG сохраняются как есть, остальные форматы преобразуются в PNG первого кадра размером до 512 пикселей. Сервер сверяет MIME с содержимым, проверяет изображение, а размер сохранённого аватара учитывает в пользовательской квоте. Ответ содержит `avatar_url`. Он также появляется в данных текущего аккаунта, поиске пользователей и списке участников чата. `GET` и `HEAD /api/v1/users/{userID}/avatar` доступны без авторизации, поэтому этот URL можно использовать прямо в `<img>`. Сервер не выдаёт ссылку на S3; прочие файлы остаются закрытыми. `DELETE /api/v1/users/me/avatar` удаляет текущий аватар, а worker очищает старый объект после замены или удаления.

Для отметок сообщения клиент явно подтверждает получение через `POST /api/v1/chats/{id}/delivered` с `{"seq": N}` и просмотр через `POST /api/v1/chats/{id}/read` с тем же телом. Просмотр также подтверждает доставку. Указатели монотонны и ограничены последним сообщением чата. Ответ содержит `delivered_seq` и `read_seq`; WebSocket-событие `receipt` содержит их вместе с `user_id`. Каждое сообщение в ответах истории, поиска и отправки содержит `receipts` по текущим получателям, вступившим до отправки, и `delivery` со счётчиками и общим статусом `sent`, `delivered` или `read`. В группе общий статус `delivered`/`read` означает подтверждение **всеми** такими получателями; частичные подтверждения видны в счётчиках и `receipts`. Сам факт отправки на сервер не считается доставкой устройству.

## События и звонки

Клиент получает одноразовый билет через `POST /api/v1/auth/websocket-ticket` с Bearer, затем соединяется с `/api/v1/ws?ticket=…`. Билет живёт 30 секунд и расходуется один раз. Команда `{"type":"sync","after_event_id":123}` повторяет доступные события; после разрыва источником истины остаётся REST-история. Соединение закрывается при отзыве сессии или исключении из чата.

В личном чате `POST /api/v1/chats/{id}/calls` с `{"kind":"audio"}` либо `video` создаёт звонок. Вызываемый пользователь отвечает через `/api/v1/calls/{id}/accept` или `/reject`; звонящий отменяет через `/cancel`, участники завершают `/end`. Отвечает первое устройство, остальные получают конфликт. После принятия выбранные сессии обмениваются по WebSocket кадрами `{"type":"offer|answer|ice","call_id":"…","data":{…}}`. SDP/ICE не сохраняются в истории. `GET /api/v1/calls/{id}/ice` выдаёт выбранному устройству временные TURN-реквизиты на 10 минут; клиент обновляет их во время долгого звонка. Сам медиапоток передаётся WebRTC, не через сервер чата.

Для уведомлений iOS создайте ключ APNs `.p8` в Apple Developer, включите Push Notifications и Background Modes (Voice over IP, Remote notifications) для App ID, затем задайте `APNS_KEY_FILE`, `APNS_KEY_ID`, `APNS_TEAM_ID` и `APNS_TOPIC` в `.env`. Тема должна совпадать с bundle ID приложения; VoIP-тема формируется добавлением `.voip`. Для отладочной установки используйте `APNS_SANDBOX=true`, для TestFlight/релиза — `false`. Ключ монтируется только в worker и только на чтение. Без этих настроек чат и звонки в открытом приложении продолжают работать, но фоновых push нет. После входа iOS регистрирует отдельные токены обычных и VoIP-уведомлений через `PUT /api/v1/push/devices/{device_id}`; при удалении сервера удаляет регистрацию. Worker отправляет уведомления об адресованных сообщениях и VoIP push о звонках через APNs. Текст сообщения в push не передаётся.

## Данные и обслуживание

PostgreSQL хранит сообщения, членство, сессии, события и задания; SeaweedFS в профиле Compose предоставляет приватный S3-совместимый бакет. Worker создаёт PNG-превью изображений и JPEG-превью видео, очищает истёкшие незавершённые загрузки и удаляет файлы по сроку хранения. Резервирование квоты учитывает одновременно загружаемые файлы. При ошибке превью оригинал остаётся доступным.

Резервируйте **вместе** тома `postgres_data` и `s3_data`, иначе ссылки на объекты потеряют соответствие. Для резервной копии PostgreSQL используйте `pg_dump` внутри контейнера и штатные средства резервирования SeaweedFS для тома S3. Перед восстановлением остановите API и worker; восстанавливайте согласованную пару снимков, затем запускайте сервисы и проверяйте `/health/ready` и выборочное скачивание.

Общий контракт API находится в [OpenAPI](api/openapi.yaml). Для мобильного приложения используйте [подробную спецификацию](api/mobile-openapi.yaml): в ней описаны типизированные запросы и ответы пользовательских методов, статусы ошибок, защищённая загрузка файлов и Range-проигрывание видео, а также кадры WebSocket в расширении `x-websocket-messages`. Административные методы в мобильный контракт не входят. Проверки разработчика:

```sh
go test ./...
go vet ./...
cd admin && npm ci && npm run build
docker compose config -q
python3 tests/integration/live_compose.py
python3 tests/integration/turn_probe.py
```

Первые три проверки работают без внешних сервисов; Go-интеграционные тесты используют `TEST_DATABASE_URL`, `TEST_S3_ENDPOINT`, `TEST_S3_ACCESS_KEY` и `TEST_S3_SECRET_KEY` для отдельной тестовой базы и бакета `familychat-test`. Два Python-сценария проверяют уже запущенный Compose; `live_compose.py` создаёт тестовые аккаунты и сообщения в его локальной базе.


### Приглашения

В админке раздел «Приглашения» создаёт ссылку `/invite/{token}`. Укажите название,
доступный пользователю адрес сервера и дату/время окончания (местное время браузера;
на сервер передаётся RFC3339). По умолчанию срок — 7 дней, максимальный — один год.
Ссылки многоразовые до истечения срока или отзыва; список показывает последние 100.
Приглашение не создаёт аккаунт и не обходит настройку самостоятельной регистрации.

Страница пытается открыть `familychat://invite?url=<encoded invitation URL>` и содержит
кнопку для повторного открытия, если браузер требует нажатия. В iOS и macOS приложение
проверяет приглашение и `/health/ready`, сохраняет сервер без дубликатов и открывает вход.
Сохранённые аккаунты других серверов не удаляются. Если приложение не установлено,
на странице есть временная ссылка `https://apps.apple.com/app/id0000000000`;
после установки приглашение нужно открыть повторно. Universal Links не используются.

Миграция `0007_invitations.sql` применяется при запуске обновлённого сервера.
Пересоберите сервер с админкой и оба клиента; уже запущенные старые сборки не умеют
обрабатывать приглашения. У reverse proxy должны быть доступны `/invite/`,
`/invite-assets/` и `/api/v1/invites/` (в поставляемом nginx уже проксируются).

### Шифрование содержимого (fc1)

Клиенты iOS/macOS шифруют текст, вложения и созданные на устройстве JPEG-превью
перед отправкой. API хранит и возвращает шифротекст, не расшифровывая обычные
запросы. Получатель расшифровывает данные перед сохранением в локальную историю
и файловый кэш. Поиск выполняется на устройстве: сначала по локальной истории,
затем по загруженным страницам сервера, без передачи поискового запроса.
Видео проигрывается из скачанного и проверенного локального файла.

Это **общий ключ сервера, не сквозное шифрование**: авторизованные пользователи
получают одну пару X25519 через `GET /api/v1/encryption/key`. Сервер также владеет
приватным ключом. Удаление аккаунта/участника запрещает дальнейшие скачивания,
но не отзывает уже полученные копии ключа и данных. Участники, имена пользователей,
названия чатов, имена/MIME/размеры файлов, даты и квитанции остаются открытыми.
Аватары по-прежнему публичны; протокол звонков не изменён. Ключи в клиентах
кэшируются только в памяти текущего подключения; локальная история остаётся
открытой по выбранной модели хранения.

Нужен HTTPS; HTTP разрешён для обмена ключами только на loopback при разработке.
Клиенты не переключаются на открытую отправку при ошибке ключа. Чтение чатов,
сообщений и файлов требует `X-Content-Encryption: fc1`; старый протокол получает
`426 encryption_required`. `/chats/{id}/search` возвращает `410 search_on_device`.

**Обновление и старые данные.** До обновления сохраните согласованную резервную
копию PostgreSQL и S3. Остановите старые `api` и `worker`, затем обновите сервер и
оба приложения. Установщик и `scripts/deploy-https.sh up` останавливают старые
процессы автоматически и подготавливают secrets. При ручном Compose после
обновления файлов проекта выполните:

```sh
docker compose stop api worker
docker compose run --rm --build key-setup
docker compose up -d --build
```

Во время первого запуска API недоступен:
миграция `0012` шифрует всю старую переписку и существующие файлы/превью, затем
удаляет старые объекты S3. Миграция возобновляема после прерывания. Текущие данные
зашифрованы, но предыдущие резервные копии, WAL/старые страницы PostgreSQL и
версии объектов внешнего S3 могут сохранять прежний открытый текст; их жизненный
цикл управляется отдельно. Превью, которых не было до миграции, не создаются
сервером заново. Новые превью создаёт отправляющий клиент.

**Ключи Docker secrets.** Публичный и приватный ключи передаются API отдельными
секретами `content_public_key` и `content_private_key`, смонтированными только для
чтения в `/run/secrets/`. API не генерирует и не изменяет их; worker их не получает.
В образе, БД и переменных окружения содержимого ключей нет.

Перед первым запуском контейнер `key-setup` создаёт пару X25519 и сохраняет её
в `secrets/content-public-key.txt` и `secrets/content-private-key.txt` (base64,
права `0400`). Для Compose в Linux файлы принадлежат UID/GID `10001:10001`, чтобы
API без root мог читать секреты. Каталог `secrets` на VPS закрыт правами `0700`.
В обычном Compose secrets основаны на файлах хоста: это не зашифрованное хранилище
Docker Swarm. [Описание Docker Compose secrets](https://docs.docker.com/compose/how-tos/use-secrets/).

При переходе с v2.0.0 подготовительный контейнер читает прежний
`encryption_keys/key.json` из тома, проверяет отпечаток в БД и экспортирует **ту же**
пару в secrets. Существующая переписка не перешифровывается. Том доступен только
подготовительному контейнеру для чтения и сохраняется как резервная копия; API
больше его не монтирует. Повторный запуск сохраняет ключи. Неполная запись с
готовым приватным ключом восстанавливается, несовпадающая пара вызывает ошибку.

Сохраняйте резервную копию обоих файлов secrets отдельно от БД и S3, с ограниченным
доступом. При обновлении с v2.0.0 сохраните также старый том `encryption_keys`.
Без исходного приватного ключа историю восстановить нельзя: при потере ключей
или несовпадении отпечатка с БД запуск останавливается, замена не генерируется.
`docker compose down -v` удаляет тома данных и не является командой обновления.
Установщик запрещает откат на релизы с прежним способом хранения ключа; команда
обслуживания обновляется до миграции и сохраняется после прерванной активации.
Для совместимости при запуске вне Docker можно явно задать `CONTENT_KEY_FILE`
с путём к прежнему JSON-файлу. В стандартном Compose этот режим не используется.

Формат для разработчиков:

- [HPKE RFC 9180](https://www.rfc-editor.org/rfc/rfc9180.html), base mode,
  DHKEM(X25519, HKDF-SHA256), HKDF-SHA256, AES-256-GCM. Используются стандартный
  Go `crypto/hpke` и Apple CryptoKit, с взаимными тестовыми векторами.
- Заголовок: ASCII `FCENC001` (8 байт), SHA-256 публичного ключа (32), HPKE
  encapsulated key (32), размер открытых данных uint64 big-endian (8).
- Далее блоки открытого текста до 1 МиБ с 16-байтным тегом каждый. Для пустых
  данных есть один блок с тегом. Каждый блок аутентифицирует весь заголовок;
  порядок задаётся счётчиком HPKE. Новый контекст создаётся для каждого объекта.
- HPKE info: `FamilyChat/v1/` + контекст. Для текста контекст
  `message:<chat_uuid>:<sender_uuid>:<client_message_uuid>`, для файла
  `file:<chat_uuid>`, для превью `preview:<chat_uuid>`; UUID в нижнем регистре.
- `text` в JSON — base64 конверта и `encrypted: true`; бинарные тела файлов
  передаются без base64. Размер тела — `80 + plaintext_size + 16 * max(1, ceil(plaintext_size / 1048576))`.
  У загрузки обязательны `X-Plaintext-Size`, `X-Content-Encryption: fc1` и обычные
  заголовки имени/MIME. Затем клиент может выполнить
  `PUT /files/{id}/preview` с зашифрованным превью до 1 МиБ открытых данных.
  До успешного PUT состояние превью — `unsupported`, после — `ready`. Ошибка
  загрузки превью не отменяет успешную загрузку оригинала и отправку вложения.
- Range относится к смещениям **шифротекста**. Неполный, изменённый или избыточный
  конверт не сохраняется как готовый открытый файл. Повтор сообщения с тем же
  `client_message_id` и теми же вложениями возвращает первую запись, даже если
  рандомизированное шифрование при повторе дало другие байты.
